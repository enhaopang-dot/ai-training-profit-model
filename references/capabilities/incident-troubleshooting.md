# 现场翻车排障路径（incident-troubleshooting）

## R — 原文规则

> "突发状况挡不住，淡定和临场应对反而让学员更信任你。"
> ——原文 §7 翻车现场（p47 翻车应对原则）

> "下午实操 MiniMax 突然崩了 + 学员强烈要求讲大纲外的多 Agent 协作……培训结束后在高铁上写修复脚本发给他们。"
> ——原文 §7 翻车现场（f35 现场翻车排障路径）

规则本体：现场翻车的应对路径 = 即时承接（情绪稳定本身是信任来源）→ 事后补救（当天写修复脚本/补救材料发学员）→ 复盘预防（核对课前 SOP 的设备检查与双版本方案是否执行到位）。预防层（u30 五件套）不在本卡重复展开。

## I — 释义

AI 企业培训的现场突发是结构性必然，不是小概率事故：演示依赖云端工具（崩溃不可控），学员动手欲强（大纲外需求必然出现）。本方法的核心重构是：翻车本身不摧毁信任，慌乱和无补救才摧毁；应对得当反而是信任建设机会（原文亲历验证：信任度不降反升）。

三层动作的分工——即时层只有心态原则（淡定、口头承接、把突发讲成真实案例），原文刻意不给"现场切换备用演示工具"的分支预案（此为已记录的原文缺口）；补救层是硬动作，要求当天产出可执行的修复材料发到学员群；预防层不新造规则，直接回查 u30 的设备七项检查与完整版/精简版双方案是否做到位。

适用前提：交付现场突发（工具故障、网络中断、学员带节奏失控）。不适用：课前准备问题（归 u30）、客户事后对交付质量不满的客诉（本卡只管现场）。

## A1 — 应用示例

- 正例 c19（亲历案例，§7 翻车现场）：下午实操时段 MiniMax 崩溃 + 学员强烈要求讲大纲外多 Agent 协作、把自己手上的 Agent 拆崩。执行路径：现场淡定承接 → 课后在高铁上写修复脚本发给学员 → 学员信任反而提升。结果：作者自述信任度增强，验证"翻车应对=信任建设机会"的重构。
- 反例 x08（§7 翻车现场，无预案版本）：现场实操只依赖单一工具 + 单一网络，工具崩溃时慌乱冷场；被学员带到大纲外内容后现场失控。机制：没有 Plan B 时，现场中断直接击穿"专业可信"这一 B 端采购前提——同样的突发，有无承接能力决定信任是加分还是清零。

## A2 — 触发场景

1. 讲课中途演示工具崩溃、断网、账号被踢，学员在场看着。
2. 学员起哄要求讲大纲外内容，或被领导临场要求"这块跳过/多讲讲"。
3. 现场把自己的操作搞砸（演示失败、数据出错），需要圆场。

语言信号："现场翻车了怎么办""工具崩了怎么救场""学员带节奏讲大纲外内容怎么处理""演示失败如何圆场""课堂突发事件应对"。

英文 trigger patterns: "live demo crashed during training", "tool failure in the middle of a workshop", "participants derailed my session", "how to handle classroom incident", "AI training contingency".

相邻区分：与 u30 课前 SOP 是"预防 vs 应对"关系——u30 管事前五件套，本卡管事中承接+事后补救，构成"预防-应对-补救"闭环；与 u34 获得感设计无关——本卡处理突发，不设计课堂体验。

## E — 执行契约

输入契约：故障描述（什么环节、什么工具、影响范围）、现场状态（学员是否在场、情绪反应）、可用备选资源（备用热点、U 盘、精简版方案）。缺失"当前处于课的哪个环节"应先询问，不能静默假设。

排障步骤（troubleshooting 分支）：

1. 症状判定（2 分钟内）：区分是工具故障、流程失控还是两者叠加。完成标准：能用一句话说清"什么坏了 / 谁被带跑了"。
2. 即时承接：不慌乱，口头承认突发 + 引导（承认突发→把突发讲成真实世界的 AI 运维案例→或宣布切换到精简版方案衔接）。完成标准：现场无冷场、教学主线不断。
   - 判停点：若判断为 1 分钟内可自行恢复（网络抖动切备用热点），恢复演示并继续，跳过步骤 3、4 的补救生产，仅做记录。
3. 纪律分支：学员要求大纲外内容 → 记录需求、承诺课后单独给材料，不现场展开（防止现场拆崩扩散）。完成标准：需求被记录且现场未失控。
4. 事后补救：当天产出修复脚本 / 补救材料发学员群（原文样本时延：下课当天，高铁上）。完成标准：每位受影响的学员收到可执行的补救物。
5. 复盘预防：核对 u30 设备七项检查与双版本方案本次是否执行到位，把故障记入课件库防复发。完成标准：产出"本次可预防项"结论（有 / 无，列明项）。

输出契约：三件套清单——现场承接话术记录、课后补救材料（已发送证据）、预防核对结论。三者齐备才算处理完成。

## B — 边界

- 反场景：课前准备检查清单不归本卡（走 u30）；客户事后对交付结果不满意的客诉处理不归本卡（本卡只管现场突发）。
- 作者警告的失败模式（x08）：只备单一工具/单一账号、无备用热点与离线素材；学员提出大纲外需求时无承接方案——慌乱冷场直接击穿"专业可信"的采购前提。
- 原文缺口（verified gaps，须如实告知用户）：无分支化现场应急预案——"工具崩了现场改用哪个替代演示/降级方案"原文未给，仅心态原则 + 事后补救（f35 已标 missing_conditions）。讲师需自建 Plan B；可结合 u30 设备清单补"备用演示环境"检查项，但这不是原文规则。
- 相邻易混淆：u30（课前 SOP 五件套）是预防层，本卡是应对+补救层；两者都被调用时先 u30 后本卡。
